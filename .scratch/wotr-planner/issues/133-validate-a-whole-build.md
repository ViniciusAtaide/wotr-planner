# Validate a whole Build in one call

Type: design
Status: resolved
Blocked by: none
Map: [WotR Build Planner](../map.md)

## Question

An agent plans a Build in its head (race, scores, a class per level, every feat and Mythic pick), then feeds it to `choose` step by step. `choose` stops at the first refused step ([104](104-mcp-server-plan.md)), so a plan with five mistakes takes five round trips. Each trip shows only the first mistake. When one refused pick is the root of later ones, the agent can't tell which mistakes are independent and which follow from another. The user (2026-11-09) asked for a `validate build` tool: the agent sends a whole Build, typed so it knows what to send, and gets back every mistake with a description, shaped like a dependency tree.

The engine already does most of this:

- **The full walk collects every failure.** `Walker::failed: Vec<Choice>` holds the choices that fail, in walk order, and `evaluate` walks to the end ([walk.rs](../../../libs/rules/src/engine/walk.rs)). Only `is_possible` and the recheck walk (`holds`) stop at the first one.
- **It throws the reason away.** A slot's pick is checked by `check_pick`, which returns the `Issue`, and the walk keeps only the place: `Err(_) => self.fail(Choice::Slot(id))` ([walk/hold.rs](../../../libs/rules/src/engine/walk/hold.rs)). `fail`'s doc says so: "Only whether one does matters … never why."
- **The reason is already a tree.** `Issue::Unmet(Unmet)` is shaped like the failing part of the prerequisite tree (`All`, `Any`, `AtLeast`, `Condition { needs, has }`, `MetLater`), and the server already renders it (`issue_reason`: "Needs BAB 6 (have 4)").
- **Failures cascade.** A failed pick isn't held, so a later pick that needs it fails too. That is the dependency the user wants to see: the later failure's unmet leaf names the earlier failed pick.
- **Every engine `Choice` has an MCP address** (`Address::choice`, [address.rs](../../../apps/mcp/src/address.rs)), so each failure can name the address the agent sent.

This doesn't reverse [39](39-impossible-states-not-validation.md) (impossible states instead of validation). The tool is diagnostics only. A Build with errors never becomes a code, and a valid one passes the same final gate as `choose` (`reopen`, through `Engine::open_link`).

## Options

The input shape:

- **A. `choose` that doesn't stop.** The same `steps` list. A refused step is recorded and skipped, and the rest are applied. Almost all of it is [choose.rs](../../../apps/mcp/src/choose.rs) already. But it depends on order: a refused class leaves that level's slots missing, so every pick there comes back as `no_such_choice` noise. The tree comes only from the order of the steps, not from the rules.
- **B. A whole `rules::Build` as JSON.** It's already serde with string keys. But `SlotId`'s JSON isn't the MCP address grammar, so the agent learns a second vocabulary, and `rules` would need `JsonSchema` derives or an MCP mirror of `Build`.
- **C. A declared Build: a map of address → value.** The same addresses and `ChoiceValue`s that `choose` takes (`{"start.race": "human", "level.1.class": {"class": "fighter"}, "slot.feat.1.general.0": "power-attack", …}`), typed by the existing `ChoiceValue` schema. The server turns each entry straight into the Build field it names (not through the offers, since the point is to find what the offers would refuse), then walks once. Order doesn't matter, it uses one vocabulary, and the tree comes from the rules.

The engine side (needed by B and C):

- **`Engine::failures(&Build) -> Vec<Failure>`**, where `Failure { choice: Choice, issue: Issue }`: `fail` takes the `Issue` from every fail site. The recheck walk ignores it, so `is_possible` and the pickers cost nothing extra.

## Open questions (with recommendations)

1. **Which input?** *Recommend:* C. It's order-free, it uses the addresses agents already copy from `todo` and `options`, and the dependency tree comes from the rules rather than from step order.
2. **The tool's name.** The user said "validate build". The other tools are single verbs (`search`, `choose`, `withdraw`, `improve`). *Recommend:* `validate`.
3. **Fail sites without a pick check** (class entry, archetype, advances, faith and alignment, path and switch at their ranks, the level cap, unknown keys). *Recommend:* each passes the `Issue` its picker already shows for the same misfit (`DeityAlignment`, `NeedsFaith`, `ClassLevelCap`, `NotFromPath`, `Unmet` for class entry). An unknown key is `NotAllowed` plus the closest keys, as `choose`'s `not_an_option` names them.
4. **Building the tree.** *Recommend:* a failure is a child of an earlier failure when one of its unmet leaves names exactly the item the earlier one would have given: the feat, option or feature it picks; the class levels of a refused class; the path of a refused path. Everything else is a root. The reason text stays the full `Unmet`, so a child still says everything it needs. The tool doesn't re-walk with the parent fixed to prove the link, which would cost one walk per failure.
5. **Picks the Build doesn't reach** (a slot of a class the level doesn't take, a rank the Build doesn't reach, a slot index the level doesn't have). The walk finds these at the end (`reached`). *Recommend:* issue `not_reached`, with the level's class and the slots that level does have, as the child of a refused class at that level when there is one.
6. **Rules no game data changes** (`Build::keeps_fixed_rules`, point-buy range and budget, skill points over a level's budget). The walk never sees these, because a link that breaks them doesn't decode. *Recommend:* checked while the declared Build is built, each its own root error (`fixed_rule`), and the walk still runs on the rest.
7. **A valid declared Build.** *Recommend:* return the same envelope as `choose` (code, link, `todo`), through `reopen`. So `validate` also builds a whole plan in one call, and `todo` lists what's still empty. Empty slots aren't errors.
8. **The error's shape.** *Recommend:* `{choice, label, issue, reason, needs, children}`. `choice` is the address, `issue` the code (as `choose`'s `rejected`), `reason` the existing text, `needs` the unmet leaves as short strings (structured, for the agent to act on), and `children` the failures it causes. Plus `count` (all failures) and `roots`.
9. **The instructions.** *Recommend:* a "Workflow" line: plan the whole Build, `validate` it, fix the roots first (their children often go away), then `choose` the rest or keep the returned code.

## Done when

The user decides. If C, server tests (in `apps/mcp/tests/server/`, declared in its `main.rs`), each in the test world or on real data:

- A declared Build with three independent mistakes returns all three as roots.
- A cascade: Power Attack refused for Strength 12 at level 1, and a later Cleave nested under it.
- The same entries in another order give the same result.
- A pick in a slot the level's class doesn't give is `not_reached`, under the refused class when there is one.
- A fixed-rule break (a skill above the character level, a point buy over 25) is a `fixed_rule` root, and the walk's errors still come back.
- A valid declared Build returns the same code as the equivalent `choose` steps.
- A forged declared Build never returns a code.

Plus a rules test for `Engine::failures` (one per fail-site kind), `scripts/proof.sh` showing `is_possible`, `evaluate` and the pickers' answers unchanged, and `scripts/check.sh` passing.

## Implicit state machines (checked before building, 2026-11-09)

The user asked whether the design adds any, in the sense of the 2026-11-09 audit and ticket 39's decision 3: state whose combinations mean more than the types say. It adds none if built as amended below. Four spots would add one if built as first written. Three things it touches already exist and stay as they are.

**Would add one, so amended:**

1. **`NotAllowed` covering "not reached".** The walk fails a pick in a slot it never reached, a class choice for a class no level takes, and a path or switch at a rank not reached. Under the first design, each would be `NotAllowed` like a wrong key, and the server would tell them apart by checking the slot against the sheet a second time. Two sources would have to agree. **Amended:** a new `Issue::NotReached`, given by those fail sites. The path, switch and first ascension's single `if unknown || not open from this path || not reached` splits into three issues (`NotAllowed`, `NotFromPath`, `NotReached`), so each failure carries its own reason.
2. **Two result fields, where the code exists only when there are no errors.** `{envelope: Option<Envelope>, failures: Vec<…>}` could hold both or neither. **Amended:** `ValidateResult` is an enum, serialised with a `status` tag: `Valid { envelope }` or `Invalid { count, failures }`.
3. **The tree stored twice.** A flat list with `caused_by` indexes beside a nested `roots` list could disagree. **Amended:** the nested `failures` (roots, each with `children`) is the only form. A failure sits under exactly one cause, the earliest in walk order. Any other failed choices its unmet leaves name are listed in `also_needs` as addresses, not as a second copy of the failure.
4. **Per-level input for a per-class choice.** `level.N.class` carries `archetype` and `advances` at every level, but the Build holds them once per class (`class_choices`). Taking the last one given would make the result depend on map order. **Amended:** the declared Build refuses (`declared_twice`; first written `conflict`, renamed by review fix 7) two different archetypes or advances for one class, whether on two levels or on a level and `class.<c>.archetype`. It refuses `level.N.skill` and `level.N.skill.<skill>` setting the same skill twice with different numbers (first written "the same way", which was ambiguous: corrected by review fix 5). `level.N` (withdraw only) isn't a declared address.

**Exist already, left as they are (not introduced here):**

- **The walker's modes.** `sheet: bool`, `probe: Option<Probe>` and `recheck: Option<RecheckWalk>` are three knobs, and `failed` is written only while `recheck` is `None`, then frozen into `recheck.broken` by `holds` (the paused walkers in `removable.rs`). The probe-plus-recheck combination is never built. `Engine::failures` adds no knob. It is `run()` with the walk's `failed` returned (the full walk already fills it and drops it), and `failed` becomes `Vec<Failure>` in place of `Vec<Choice>`. The paused walkers clone it, and a possible Build has none, so it costs nothing there.
- **A stray racial ability.** `BuildStart.racial_ability` means something only when the race chooses one. The walk ignores it on a race that doesn't (`racial_amounts`), and the codec keeps it. Pickers clear it, so only a hand-made link holds one. This is the "Build is a plain record on purpose" case the audit assessed. **Here:** the declared Build refuses `start.racial-ability` on a race (or subrace) without a chosen bonus (`not_an_option`), so `validate` never returns a code carrying one. The walk stays as it is: failing it there would make those hand-made links stale.
- **The silent edits.** `Build::apply` ignores an edit that breaks a fixed rule, and `Engine::apply` drops what an unreached rank holds. Both are right for the sheet. **Here:** the declared Build sets the Build's fields directly rather than through either, so nothing is dropped before the walk sees it. The fixed rules (`keeps_fixed_rules`, `PointBuy::try_from`) are checked when it's built, each as a `fixed_rule` root.

## Choices settled

The user took every recommendation in "Open questions", as amended by "Implicit state machines" (the amendments win where they differ), 2026-11-09:

1. **C, a declared Build**: a map of address → `ChoiceValue`, read straight into the Build's fields (never through the offers, `Build::apply` or `Engine::apply`), then one walk.
2. **`validate`**.
3. **Every fail site gives an `Issue`**: `fail(at, issue)`. A slot's pick, `check_pick`'s issue; the class on first entry, `Unmet` (the class's own entry prerequisites), and its archetype `Unmet` or `NotAllowed` (a key the data lacks, another class's); the class level past the table, `ClassLevelCap`; the faith and alignment, `faith_misfit`'s (`DeityAlignment`, `NeedsFaith`). An unknown key (race, subrace, deity, background, class, skill) and an advancement the prestige class can't take are `NotAllowed` (an unknown key became `UnknownKey` with review fix 8). New **`Issue::NotReached`** (amendment 1) for a pick in a slot the walk never reached, a class choice for a class no level takes, and the first ascension, path or switch while the Build doesn't reach its rank. The first ascension's, path's and switch's single check is split: unknown (or not a path that rank takes) `NotAllowed`, then a switch not open from the Build's path `NotFromPath`, then not reached `NotReached`. The server names the closest keys for an unknown one, as `choose`'s `not_an_option` does.
4. **The tree** (amendment 3): one nested `failures` list. A failure sits under the earliest earlier failure that one of its unmet leaves names (the feat, option or mythic pick it picks, an option's chosen and granted feats and the features of its rows; the class levels and the features of a refused class; a refused archetype), or that it can't be reached without (point 5); the other failures it names are `also_needs`, by address. No walk to prove a link.
5. **`not_reached`** sits under the refused class of the slot's level when there is one; a path slot under its rank's path choice, a mythic selection or extra slot under its rank's general pick.
6. **Fixed rules are `fixed_rule` roots**, checked while the declared Build is built and left out of it, so the walk runs on the rest.
7. **A valid declared Build returns `choose`'s envelope** (`build`, `link`, `todo`) through `reopen`.
8. **The shape** (amendment 2): `ValidateResult`, tagged `status`: `{"status": "valid", build, link, todo}` or `{"status": "invalid", count, failures}`; each failure `{choice, label, issue, reason, needs, also_needs, children}`.
9. **A "Planned whole" paragraph in the instructions' Workflow.**

Amendment 4 (conflicts) and the stray racial ability (`not_an_option`) are built as written. Settled while building (the smallest choice consistent with the map's Notes):

10. **The argument is `choices`** (`{"choices": {address: value}}`): every other tool's `build` is a code.
11. **A character level past the level cap** fails `CharacterLevel` with `NotReached`, reported at `level.N.class` (the address declared; `level.N` isn't one), with the cap from the sheet.
12. **Skill points spent past a level's** fail with `NotAllowed` (no picker shows it: the steppers stop there); the server's reason reads the level's points off the sheet ("Level 1 spends 4 skill points of its 3"). They are the walk's, not a `fixed_rule`: this corrects question 6's recommendation (review fix 4, below).
13. **The point buy**: a score outside 7 to 18 is a `fixed_rule` at its address and walked as 10; scores over the budget are one `fixed_rule` at the highest score's address (label "Point buy"), and the rest is walked with every score 10. Failures whose unmet leaves name a score sit under it (an ability increase refused for a fixed rule likewise).
14. **Levels run from 1 with no gap.** The first missing `level.N.class` below a declared one is `missing_level`; each later declared level is `not_reached` under it (and their slots under them). An increase or skill ranks past the last level are `not_reached` under that level's class.
15. **Declared twice** (`declared_twice`, first `conflict`: review fix 7): two spellings of one address with different values (`start.score.str` and `start.score.Strength`); two archetypes or advancement sets for one class (the class is then walked without); `level.N.skill`'s map and `level.N.skill.<skill>` giving one skill different ranks (the same number given both ways is one declaration, as an archetype given the same at each level is); `start.race` naming one subrace and `start.subrace` another.
16. **`class.<class>.advances` and `level.N` aren't declared addresses** (`no_such_choice`): advances come in `level.N.class`'s value, since a `ChoiceValue` has no list of classes on its own; `level.N` is `withdraw`'s.
17. **A slot's pick kind comes from its slot**: a feat for `feat`, `option-feat` and `path-feat` slots, an option for the selection slots, a mythic ability or feat by `slot.mythic.R`'s rank, and for `slot.mythic-extra.R` a mythic ability after Extra Mythic Ability (the declared general pick's `extra_pick`), else a feat. A value is read as the item's kind of value (`parameter_text`, case ignored); an item that needs one given by its key alone is `needs_parameter` (unless its value may stay open, as `choose` allows); a value for an item that takes none is `not_an_option`.
18. **`start.race` with a subrace's key sets the race and subrace**, as `choose` takes it; `start.subrace` alone sets its race too.
19. **Every class a level takes gets a class choice**, the default when nothing is declared, as `choose`'s class edit gives one, so a valid declaration's code is `choose`'s.
20. **`needs`** is each part of the unmet "and" in the engine's words without "Needs " ("Str 13 (have 12)", "power-attack"); an "or" stays one string.
21. **The order**: what the declaration refuses, in Build order (`Address` order, text that isn't an address first), then the walk's failures in walk order. A failure's parent always comes before it.
22. **Two walks for an invalid Build**: `Engine::failures` (one walk, no sheet) and `evaluate`, whose sheet words the labels and reasons (a level's slots); a valid one costs what `choose`'s final gate does. Still no walk per failure.

GLOSSARY: **Declared Build**, **Failure** and (review fix 8) **Unknown key**.

Review fixes (the two-axis code review of 2026-11-09, user: "Fix them all"), by the review's numbers:

1. **A pick refused while reading holds its dependents.** A slot's `needs_parameter`, a value that isn't one, a value given with an item that takes none, and a slot declared twice now give what the pick would have given (both picks, for a slot declared twice), as the walk's refused picks do, so a later pick that needs it sits under it.
2. **The order test.** An object's keys reach the server as a `serde_json::Map`, a sorted map (`preserve_order` is off), so no tool call can carry two orders: the server test `the_order_of_the_entries_doesnt_matter` claimed nothing and is gone. In its place, a unit test in `validate/declare.rs` feeds `Declared::read` (which now takes the entries as any iterator) the same entries forwards, backwards and in every rotation, refusals included, and gets the same Build and refusals.
3. **A rules test for an archetype that fails its own prerequisites** (`Unmet`: the Eldritch Scoundrel for a dwarf).
4. **Skill points over a level's budget stay the walk's check** (`NotAllowed`, with the sheet's reason). This corrects question 6's recommendation: the budget depends on the class, Intelligence and the race, so it isn't a fixed rule, and checking it while reading the declaration would make two sources agree.
5. **One skill declared by both `level.N.skill` and `level.N.skill.<skill>`** is refused only when the numbers differ, as with archetypes. This corrects amendment 4's "the same way", which was ambiguous; it now reads "with different numbers".
6. **No link for "the path of a refused path"** (question 4): no prerequisite names a path, so there is nothing to link by name. A refused path holds only its rank's unreached path slots (point 5). The archetype link stays.
7. **`conflict` is `declared_twice`**: GLOSSARY's **Removable** avoids "conflict" for something else.
8. **`Issue::UnknownKey`**: the walk says when a key is one the game data lacks (a slot's item in `check_pick`, a race, subrace, deity, background, class, archetype, skill, an advanced class, the first ascension's, path's and switch's path), and `NotAllowed` keeps "not taken here" (a feat outside the slot's list, a subrace of another race, an archetype of another class, a path that rank doesn't take). The server words a failure by its issue alone and reads the game data only to name the closest keys. A declared pick's value is read through the new `Engine::value_kind(&Pick)` (`None` for an unknown key), so the server no longer checks whether an item exists itself. No picker shows either issue.
9. **The map's Notes bullet for this ticket is gone**; its Decisions line stays.
10. **Shared code.** `similar::nearest` and `similar::closest_note` are the one ranking and wording of near names, which `choose`'s `not_an_option` (byte for byte as before: its tests pass unchanged) and `validate`'s closest keys both use. `Address::label`, `Address::place` and `Address::placed` are the one label per address, which `todo` and `validate` both use. `Engine::path_fit`, `first_ascension_fit` and `switch_fit` say why a path, first ascension or switch can't be taken (`UnknownKey`, `NotAllowed`, `NotFromPath`), and `chosen_path`, `first_ascension_option`, `chosen_switch` and the walk's check all read them; the walk's three blocks are one loop.
11. **Codes spelt once**: `error.rs` owns `NO_SUCH_CHOICE`, `NOT_AN_OPTION` and `NEEDS_PARAMETER`, and `validate`'s `Refused` enum gives each declaration code (`declared_twice`, `fixed_rule`, `missing_level`, `not_reached` through `issue_code`).
12. **A failure's place is `At::Unparsed(String)` or `At::Address(Address)`**, and its issue `Why::Walk(Issue)` or `Why::Refused(Refused)`: the unmet prerequisite is read from the issue when needed (its `needs` when worded, its leaves when linked), not stored twice.
13. **`Gathered` is passed whole** to the point buy, the racial ability, the levels and the class choices.
14. **`validate/` is a module folder**: `mod.rs` (the tool, `Refused`, the closest-keys hint), `declare.rs` (reading), `wording.rs` (the walk's failures worded) and `tree.rs` (a failure, what it gives, the tree); labels moved to `address.rs` (fix 10).
15. **Doc comments** for `or_none`, `Node::giving` and `Node::under`.

The engine keeps why each choice fails: `Engine::failures(&Build)` lists every `Failure { choice, issue }` in walk order from one walk, with a new `Issue::NotReached` for what the Build never reaches, a new `Issue::UnknownKey` for a key the game data lacks (`NotAllowed` keeps "not taken here"), and the path checks split into `UnknownKey`, `NotAllowed`, `NotFromPath` and `NotReached`; `is_possible`, `evaluate`, the pickers and `removable` answer exactly as before (the proof: 2,163 Builds, no difference). The MCP server's new tool `validate` takes a whole Build as `{"choices": {address: value}}`, the values `choose` takes, in any order. It reads them straight into a Build, refusing what the walk can't see (an address that isn't one, a wrong value, a choice `declared_twice`, a `missing_level`, a `fixed_rule` break, a racial ability for a race without one) while still walking the rest, and returns `{"status": "valid"}` with the envelope `choose` would have made, or `{"status": "invalid", count, failures}`: every failure once, each under the earliest one it needs (Power Attack refused for Strength 12 holds the Cleave that needs it; a refused class holds the picks in slots its level doesn't give), with `needs`, `also_needs` and `children`. An invalid declared Build never gets a code.
