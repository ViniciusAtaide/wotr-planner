# Faster edits and pickers

Type: task
Status: resolved
Blocked by: 50, 51, 52
Map: [WotR Build Planner](../map.md)

## Question

The UI benchmark (2026-11-02, release build, snapshot 174ec14; report and scripts in the scratchpad's `bench/`: `results/summary.md`, `scripts/`, `buildlinks/`, `serve-release.sh`) found what a phone user feels. Fix #1–#4 below; leave #5 (a binary game-data format) out.

1. **`Engine::removable` on every edit** (`libs/ui/src/planner.rs` memo, read per row in `libs/ui/src/grid.rs`; `libs/rules/src/engine.rs` `removable`): walks every choice (~260 on a 40-level Build, each from its level to the end), 130–150 ms of each 150–220 ms edit at 4× CPU throttling. The grid needs only the class rows' answer; the picker header needs one choice's answer when it opens. Ask only for those (e.g. class-level removability for the grid, `is_removable(build, &choice)` for an open picker), and make the recheck walk record failures only (no sheet clones) and stop at the first failure.
2. **Opening a level-1 slot picker in a long Build** (`Engine::options`, `recheck.later` per candidate; `class_options` likewise): 150–280 ms at 4×. Re-walk only candidates a later choice could depend on (held later, named in a later prerequisite or `Not`, or granting slots, features, ability or skill changes), or show `check_pick`'s list at once and fill the "breaks later" locks a frame later. The result must stay exact: an option shown open must never break a later choice.
3. **Build start controls call `allows` repeatedly** (`libs/ui/src/start.rs` point buy, racial ability, skills panel; `libs/ui/src/picker.rs` race and background pickers): 18 calls per edit while the panel is open (+~54 ms at 4×), 47/37 on opening race/background. Share one recheck across a panel's calls (e.g. `allows_many`), fold the Build start once level 1 exists, and fill the race/background lists after the first paint as the slot picker does.
4. **Payload:** no compression, no caching, and the game data downloads only after hydration (15.3 s cold on slow 4G, 3.4 s with brotli; every repeat visit re-downloads 1.5 MB, because the server fn is a POST). Add a compression layer (brotli/gzip), serve the game data as a cacheable GET (content hash, `Cache-Control: immutable`), and start that download as early as the wasm.

## Answer

**Done.** On the 40-level Build at 4× throttling (Fold cover screen), a pick paints in 21 ms (median; was 140) and the level-1 feat picker opens in 37 ms (was 170). The engine's answers are byte-identical to HEAD's over 1,030 Builds. The game data is served compressed (1.50 MB → 110 KB brotli) and cached: a repeat visit transfers 0 bytes of it. No schema, game-data, `Build` or link change.

### What changed

**#1, removable on every edit.**
- Recheck walks (`Walker::holds`) keep no sheet: no state clone per level.
- They stop at the first choice that fails outside the edit's own.
- A pick for a level's slot that the level didn't reach fails as soon as that level is walked, not at the end of the walk. Removing a class therefore usually stops at its own level.
- `Recheck`'s paused walks are filled only as far as an edit needs.
- New: `Engine::removable_classes(build) -> BTreeSet<u8>`, which the grid's class buttons use (one memo per edit), and `Engine::is_removable(build, &choice)`, which the picker header's "× Remove" uses when it opens.
- `removable` stays, through the same walks, for tests and the proof.
- `is_possible` (and so `open_link`) uses the same fail-fast walk.
- Gain at fold ×4: per-edit engine time 120–125 → 5 ms. Paint after an edit on legend40: 138–177 → 17–28 ms.

**#2, the level-1 picker in long Builds.**
- `options` lists `named_feats`, the feats a walk of the Build can look at: each feat picked, each option's chosen feat, and the feats in the prerequisites of the picks and of the Build's classes and archetypes (in `Not` too).
- Holding a feat changes only that feat's entries in the state, and every later read is by key. So a feat pick outside that set fails later exactly what the slot left empty fails. That walk is done once (`later_walked`, which walks even when the slot is already empty) and shared by all such candidates.
- Every other candidate is walked as before, fail-fast.
- `class_options` gets only the faster walks.
- Gain at fold ×4: `options` 141 → 9 ms on legend40 and 64 → 5 ms on fighter20. The class picker at level 7 of multi_prestige20 went 105 → 53 ms (paint 138 → 84).

**#3, the Build start's repeated `allows`.**
- `Engine::allows_many(build, &edits)` shares one `Recheck` across edits; the UI's `Planner::allows_many` wraps it.
- Each panel asks once: the point buy's 12 steps, the racial ability, the skills panel's steps, the alignment wheel, the ability increase picker, and the race and background lists.
- Start edits walk from the Build start anyway, so most of the saving comes from the fail-fast walks without a sheet.
- The race and background lists fill after the first paint (`after_paint`, as the slot picker does).
- The Build start folds itself when level 1 is added (`BuildStartPanel`'s effect). Reopened, it stays open.
- Gain at fold ×4: a point-buy step 177 → 27 ms (allows 43 ms ×18 → `allows_many` 10 ms ×2). Opening the race picker 117 → 33 ms, the background picker 97 → 47 ms.

**#4, payload.**
- `apps/backend` wraps every response in tower-http's `CompressionLayer` (brotli quality 4 by default, or gzip).
- The game data is serialised once at startup into `GameDataFile` (`apps/backend/src/game_data.rs`). It is served at `GET /game-data/<first 16 hex digits of its SHA-256>.json` with `Cache-Control: public, max-age=31536000, immutable`; any other name there is a 404. A reseed changes the hash, and so the URL, on the next start.
- The shell's head has `<link id="game-data" rel="preload" href=… as="fetch" crossorigin="anonymous">` (`app::GameDataPreload`, URL from the `GameDataUrl` context), so its download starts with the wasm's.
- The sheet `fetch`es the same URL (`libs/ui/src/game_data.rs`), and the browser hands it the preloaded response.
- The `get_game_data` server fn and its `Arc<GameData>` context are gone.
- Measured (`repeat.js`, legend40):

  | | game data | wasm | starts at |
  |---|---|---|---|
  | HEAD, first visit | POST, 1,504,570 B | 1,467,186 B | 21 ms (after hydration) |
  | HEAD, repeat visit | POST, 1,504,570 B again | 0 B | 24 ms |
  | now, first visit | GET br, 110,436 B | br, 538,210 B | 3.5 ms (with the wasm) |
  | now, repeat visit | GET, **0 B** (cache) | 0 B | 2.2 ms |

- Slow 4G cold load of legend40 at fold ×4 (median of 3): game data done 14,878 → 1,439 ms, wasm done 7,505 → 3,477 ms, sheet painted 15,242 → **3,726 ms**.
- Unit tests in `apps/backend` cover the URL hash, the headers, brotli and gzip, and the 404.
- On localhost the on-the-fly compression of the wasm costs about 20 ms at ×4 (`wasmEnd` 13 → 35 ms), so the blank Build's cold paint is 8 ms slower there (241 → 249). Precompressed `.br` files would remove that; not done.

### Proof

The proof program is `t48/proof/main.rs`, with ticket 47's Build makers in `t48/proof/t47.rs`. It was compiled twice: `t48/proof-old` against HEAD's archived rules, and `t48/proof-new` against these.

- **Builds (1,030):** ticket 47's 453 proof Builds (which carry ticket 42's sets forward: every class and archetype to 20, the prestige classes, the targeted, option, cleanup, gap, decision, talent and follow-up Builds); the benchmark's 6; 369 "full" Builds (each possible one of ticket 47's with every slot, ability increase and skill point filled from the open choices by a seeded generator, plus a path from MR 3); and the 202 Path-switched variants those full Builds' switch pickers leave open.
- **Compared per Build:** whether it's possible; the sheet (Debug, hashed); `removable`; every slot's `options` with statuses (23,016 pickers, 9,025,495 options, 1,761,305 open); the class picker at every level and one past the end (15,947); the path and switch pickers; and `allows` for 569,064 edits (every start a start picker or point-buy step offers, each level's ability increases and skill steps, each pick cleared, Remove level, the path and switch unset, a name).
- **Result:** `proof-old.jsonl` and `proof-new.jsonl` are **byte-identical** (5.8 MB, md5 `4271666e…`).
- **New APIs:** proof-new also asserted, for every Build, that `is_removable` answers each choice as `removable` does (52,457 removable choices among the Builds' choices), that `removable_classes` is `removable`'s class levels, and that `allows_many` gives the battery's 569,064 answers. All hold.
