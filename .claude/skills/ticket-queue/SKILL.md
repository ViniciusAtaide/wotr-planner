# Running a queue of tickets

You are the main session: you answer questions, order the work, review, merge and run the heavy checks. Subagents research, build and review. `CLAUDE.md`'s "Parallel agents" holds the limits; this is the order of the work.

## Steps

1. **Look at who else is here.** `git status` and `git log` in the main checkout, `git worktree list`, and `ps` for `cargo`. Another session's uncommitted edits to `map.md`, or its builder, change what you may touch and how many lanes you get: two builders on the machine, theirs included. Done when you can name every other writer and builder.
2. **Read the tickets** and each one's `Model:` line. Commit ticket files that are still uncommitted, so worktrees see them.
3. **Research, all at once.** One read-only agent per ticket, on the ticket's build model. It edits nothing; in a lane no builder is using, one cargo command at a time, it may run what shows what the slice will need: a writer's `--dry-run`, and the filtered tests the slice will un-ignore or that pin its entries (`gold::` among them), on the base. Three slices met needs at build time that a run at research would have shown (306s's new selection and engine change, 308d's `rules` reader, 308e's closed slayer path), so a slice lists each test it un-ignores with what that test needs to pass. The rest of the report: the facts from the guide and the code, the edit list (each file, function and data family, with what changes in it), the tests planned by name, and every open question with its evidence, options and a recommendation. A ticket the edit list shows to be bigger than about 10 minutes of building (one concept, a handful of files, one or two tests) is split into a chain of such tickets here, before any builder starts: 310, briefed with its function and line, built in 10 minutes; tickets explored by their builders took 75–110 (`research/builder-timing-2026-11-16.md`). Reading costs no CPU, so these run side by side. Each report, and every decision made on it (step 4), is written to `.scratch/wotr-planner/research/<ticket>/` and committed with the ticket files; only bulky dumps stay in the scratchpad, which a reboot can clear. **No builder starts on a ticket without its research report there** (298 went to a builder without one, hit a scope decision and waited about 7 hours).
4. **Answer.** A question the guide, a map decision or the data's own convention settles, you answer and record as yours. The rest go to the user in one round, each with a recommendation; work that doesn't hang on them carries on.
5. **Sort into lanes** by the files each ticket touches. Tickets that share a file go in one lane, in order. Create one worktree per lane from local `main` (`git worktree add -b ticket/<n>-<slug> .claude/worktrees/lane-<name> main`, then check the base). A lane keeps its worktree for the whole queue, so its `target/` stays warm.
6. **Build.** Brief a `ticket-builder` with the worktree, branch, base, the files it may touch, the decisions, and the path of the research report in `research/<ticket>/`. Resume the research agent for a small ticket; for a fix round on an agent whose context has grown past about 300k tokens, start a fresh builder with a pointed brief.
   **Watchdog:** the main session acts only when a message or notification arrives, so a silent subagent needs a timer. In the same message that launches a builder, start a background `sleep` (Bash, `run_in_background`) for the slice's own estimate (the minutes on its heading in `research/<ticket>/slices.md`) or 30 minutes, whichever is longer (the user, 2026-11-17: three rescues at 30 minutes found 50–75-minute slices on schedule); its completion notification is the check. When it fires and the builder hasn't reported, or whenever a subagent has run past that time without reporting (the task notification's `duration_ms`, or `ListAgents`'s "started" age), spawn a rescue helper on Fable 5.2 (`model: fable`) with the `subagent-rescue` skill. Give it the subagent's brief and worktree. Set its `effort` to fit what it must judge (the user, 2026-11-17):
- `medium` when the question is only whether it's stalled: a test or docs slice, a clean diff, no failing results;
- `high` for a data or writer slice with failing tests, a census to read, or a game fact to check;
- `xhigh` when the subagent is stuck on an engine change, or the diff may hold a move away from the game across many entries. It diagnoses read-only, hands back an unblock plan to act on, and appends a retro to `research/rescue-retros.md`; apply the retro's proposed changes. One helper per subagent; don't stop the subagent before its plan comes back.

   **Keep the machine awake** for the length of a queue: request it (the app's keep-awake, `until: session_idle`) before the first builder. On battery, a Mac in maintenance sleep stretched 306j's 4-minute test run past an hour.
7. **Review before the merge,** on the model the ticket names, with `ticket-reviewer`. Read the diff yourself too. A builder's report is a claim.
8. **Merge** into local `main` with `git -C <main> merge --no-ff`, then move the lane to the next ticket's branch from `main`. A lane that worked beside another merges `main` into its branch and reruns its scoped checks first. When another session has staged files in the main checkout, a true merge there refuses: make the merge commit in the lane (`git switch -c integrate/<n> main`, `git merge --no-ff ticket/<n>-…`), then `git -C <main> merge --ff-only integrate/<n>`, which leaves their index and working tree alone. Commit your own files there with `git commit -m … -- <paths>`.
9. **Close the queue,** with every lane idle: a code review of the merged range; `scripts/queue-checks.sh`; the self-checks' long runs, a heavy run (`cargo test --release -p corpus -- --ignored`, then `cargo test --release -p seeds --test game_data agreement -- --ignored`); a QA session (the `qa-session` skill). Fix what the queue caused; write a ticket for what is older.
10. **Record.** One entry per ticket and one for the queue's checks in the map; follow-up tickets; then offer to remove the lane worktrees and merged branches.

## Hazards met before

- **`cd` in your own Bash** moves the session's directory under running subagents. Use `git -C` and absolute paths.
- **A file created through the IDE is staged at once,** and a staged new file makes `git merge` refuse. `git restore --staged <file>` first, or commit it.
- **The dev server reads the game data at startup.** After a data-only merge it serves the old data until it restarts; check before reproducing through the MCP tools.
- **Count pins conflict at nearly every merge** (`prerequisites_as_components`' `(moved, fields)`, `data.rs`'s list counts): two lanes each move the same number from the base. Resolve by sum, base plus each side's delta (635 → 649 and 635 → 636 merge as 650), keep both sides' comments, and let the merged tree's tests confirm it.
- **A shell glob beside `git -C <other worktree>`** expands in your shell's directory, not in that worktree: name the files, or list them from inside it (`$(cd <wt> && ls …)`). The 308a–f ticket files missed their commit this way.
- **A design you steer a builder to is a claim too.** When you override a research agent's recommended shape, ask the reviewer to attack that choice by name.
